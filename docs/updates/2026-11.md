## U-20261115-05 · 2026-11-15 · The embedded JupyterLab asks for a token · #done #security #jupyter

- **What**: closes `progress.md` #92 as the owner answered: a token is made for each launch and the tab's view loads with it. The server had none, so the loopback bind kept other machines out but not the other accounts of a shared machine (RDS, a lab Linux box), which got a kernel running as the IDE's user.
- **How**: `JupyterLauncherThread.token` (`secrets.token_urlsafe(32)`) is given to the server as `JUPYTER_TOKEN` in its environment, not as an argument, which another account can read; the two arguments that forced an empty token are gone. `JupyterLabWidget.load_lab()` adds `?token=` to the first request, and `LabPage.lab_url` keeps the address without it. The launcher still announces the plain address, so the token is in no signal and no log.
- **Checked on a real server** (jupyter_server 2.17.0, started the way the tab starts it): `/api/status` answers 403 without the token and with a wrong one, 200 with it; `/lab?token=…` answers 200; no argument holds the token.
- **Side effect**: a lab link that opens in the system's browser (a link for a new tab) now meets the login page there, since that browser has no cookie.
- **Files**: `pybreeze/pybreeze_ui/jupyter_lab_gui/jupyter_lab_thread.py`, `jupyter_lab_widget.py`, `CLAUDE.md` (Security › JupyterLab), `docs/source/{Eng,Zh}/jupyter_lab.rst`.

## U-20261115-07 · 2026-11-15 · AI panels may use a local endpoint after asking · #done #security #ai

- **What**: closes `progress.md` #111 as the owner decided. AI Code Review, CoT Code Review and Skill Send refused every endpoint on this machine or a private network, so a local model server could not be used. `validate_url` now raises `LocalAddressNeedsApprovalError` (still an `UnsafeURLError`) when every refused address is loopback or a private network's; the request thread reports it, and the panel's `LocalEndpointGate` asks once the thread has ended, naming the host and the addresses, with No as the default. On a Yes the panel sends again with those addresses as `allowed_local`, and the request runs inside `approved_local_addresses(...)`, so the check made at the connection accepts exactly those addresses: a name that then resolves to another private address is refused. Link-local (the metadata service), CGNAT, multicast, reserved and unspecified addresses, and IPv6 forms that carry an IPv4 address, can never be allowed. The answer is kept in the panel's memory only. DNS is still resolved on the worker thread.
- **Files**: `pybreeze/utils/network/url_validation.py`, `pybreeze/utils/network/public_http.py`, `pybreeze/pybreeze_ui/local_endpoint.py` (new), the three panels and their threads, both language dictionaries (1000 keys), `CLAUDE.md` (Security › Network), READMEs, `docs/source/{Eng,Zh}/ai_tools.rst` and the troubleshooting pages, `architecture.md`, `architecture_explore.md`.

## U-20261115-08 · 2026-11-15 · The MCP tab follows a server that changes what it offers · #done #mcp #ui

- **What**: closes `progress.md` #132. A server's `notifications/tools/list_changed` (and the ones for resources and prompts) reached the thread that reads the server and went no further, so a new tool was seen only after connecting again. The tab now gives each client a listener that does one thing on that thread: emit `McpClientGUI.list_changed`, which Qt delivers on the UI thread. The lists named are read again on an `McpWorker`, 150 ms after the last notification so that several arrive as one reading, and after whatever call is on its way. The pages are filled again without losing work: the selected tool, resource or prompt stays selected, the arguments typed for it and the last result stay, and what the server now says of it is shown. The arguments box is started once for an item, so typing in the tools filter no longer starts it again either. A trusted tool that the new list describes differently is asked about again for the rest of the session; a tool the server added is not trusted. A notification from a server already let go of is dropped.
- **Files**: `pybreeze/utils/mcp/mcp_client.py` (`LIST_CHANGED`, `changed_list`), `pybreeze/pybreeze_ui/mcp_gui/mcp_client_gui.py`, `pybreeze/pybreeze_ui/mcp_gui/mcp_panels.py`, both language dictionaries (1002 keys), `test/test_utils/fixtures/mcp/fake_server.py` (`--changing`), READMEs, `docs/source/{Eng,Zh}/menu_tools.rst` and the MCP tutorial, `CLAUDE.md` (Security › MCP), `architecture.md`, `architecture_explore.md`.
- **Evidence**: `test_mcp_client_gui.py` (the sections "A server that changes what it offers" and "The pages, filled again"), `test_mcp_client.py::test_a_notification_names_the_list_that_changed`.
- **Open items**: `notifications/resources/updated` (one resource's content changed) is not followed: the tab subscribes to no resource.
